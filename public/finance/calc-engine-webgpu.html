Prototype analysis — what this proves (and what it does not)

This page is a prototype: WebGPU visualizes the FHA Streamline DAG and verifies an integer-cent chain. The live product worksheet still runs on CPU calcMath + CalculationsEngine.

Microseconds vs milliseconds

CPU calcMath (~11 cells) µs

A microsecond is 1/1,000,000 of a second. The loan chain finishes in tens of microseconds — already “free” for keystroke UI.

WebGPU kernel + readback ms

A millisecond is 1/1,000 of a second — 1,000× a microsecond. GPU setup, dispatch, and CPU readback usually land in a few milliseconds for this tiny DAG.

Bottom line: for one loan, GPU is slower. Humans notice ~100 ms; both paths still feel instant — the point is engineering cost, not UX lag.

Precision (formal claims)

  • f32 dollar floats cannot safely round FHA-scale cents (see the drift exhibit above).
  • Integer cents (i32) make add / subtract / min / floor-to-dollar exact for typical loan sizes (~$21M max in cents).
  • GPU does not add precision — the integer representation does. Same rules run on CPU via fhaLoanAmountIntegerCents.
  • UFMIP uses a named half-up bps rule — research/demo only, not HUD-certified.

Where this could matter theoretically

  • Batch / stress grids — thousands of independent scenarios in one dispatch (rate × balance × factor), not one keystroke chain.
  • Teach / audit / demos — pulse the DAG so processors see why G15 → G30 cascade; Unit Test / training reels.
  • Second-opinion verifier — CI or pre-write check: GPU cents ≡ CPU integer cents, while Encompass UI stays on float calcMath.

Where not to use it

  • Replacing the live FHA Loan Amount worksheet recalculation.
  • Trusting default GPU f32 dollars for money.
  • Expecting a speed-up on an 11-node sequential DAG.

Thesis: WebGPU here is a visual + exact-cent research layer. Product calculators stay on CPU. Scale the kernel only when the workload is many independent loans, not one form.
